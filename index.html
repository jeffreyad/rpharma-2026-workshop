1 Skills overview

1.1 What is a “skill”?

A skill is a reusable, model-agnostic workflow an AI coding agent loads on demand:

  • A SKILL.md file — step-by-step instructions for one class of task
  • Supporting reference files — conventions, function-selection logic, failure modes
  • Bundled scripts — R / Python the agent runs in your environment

The agent reads the skill only when your request matches it, then follows it instead of improvising.

Contrast with a raw prompt: a prompt is transient and lives in one person’s head or chat history. A skill is version-controlled, reviewable, and encodes institutional knowledge — “here is how we derive ADSL” — so every run starts from the same vetted baseline.

Analogy: an SOP that the agent actually executes, not just reads.

1.2 Why skills matter for clinical programming

Clinical programming is high-stakes, convention-heavy, and traceability-driven. A skill lets you encode, once:

  • CDISC / ADaMIG conventions ("Y"/NA flags, study-day rules, date imputation direction)
  • Function-selection logic (when derive_vars_merged() vs derive_vars_merged_lookup())
  • QC scaffolding (stopifnot() assertions, # REVIEW: markers at every protocol-specific decision)

The agent then reproduces that discipline on every run.

The point is consistency and traceability, not just speed. A skilled run produces code that already has review markers where a human must make a protocol call — the reviewer’s attention is directed, not diffused.

Same argument on the biostatistics side: the group sequential design skill encodes scope checks, the N-first algorithm, IA-timing constraints, and a mandatory simulation-verification step.

1.3 Skills vs. no skills — ADaM benchmarks

Community A/B benchmarks in pharma-skills — the same task, an agent with vs without the skill, scored against a methodology rubric:

Skill / task With skill Without skill
ADSL derivation (34-point rubric) 100% 62%
ADSL safety flags — SAFFL / ITTFL / PPROTFL 83% 46%
ADAE derivation 94% 33%
ADLB derivation 94% 48%
ADVS (BDS) derivation 88% 36%

The gap is mostly admiral-idiom compliance + QC annotations, not whether the numbers come out right.

Source: benchmark-runner results posted as comments on the [benchmark] issues in RConsortium/pharma-skills — #137, #147, #148, #149, #126, #165. Single runs, claude-sonnet-4-6, pharmaversesdtm → pharmaverseadam data, May–Jul 2026; skill versions vary by run.

[CONFIRM WITH JEFF: confirm these are the runs/numbers you want on-slide, and whether to cite a specific skill SHA / date.]

What the gap actually is: both agents usually compute the right values. The skill-guided agent uses admiral functions, places # REVIEW: comments at every protocol-specific decision, and adds stopifnot() QC guards; the unaided agent uses base dplyr/lubridate, no review markers, and sometimes leaves DOMAIN in or keeps SDTM "Y"/"N" flags — code that would draw immediate QC findings.

Honest caveats to say out loud:

  • On short rubrics or template-shaped tasks (basic two-arm ADSL, the admiral ADVS vignette pattern, trivial derive_vars_cat / compute_rr conversions) the measured gap is ~zero — the base model already knows these.
  • The skill runs roughly 1.5–9× more tokens.
  • A couple of individual runs the skill scored slightly worse (e.g. duplicate baseline flags) — this is A/B benchmarking, not a guaranteed win every time.

1.4 Skills vs. no skills — group sequential design

group-sequential-design skill — 15 trial-design scenarios, 3 models (Claude Sonnet / Opus, Gemini Flash), April 2026:

With skill Without skill
Avg score across scenarios 73% 51%
Scenario wins 10 3
Ties 2 2

Standouts: 83% vs 0% — no-skill crashed on gsSurv() across 7 attempts; 100% vs 44% — skill self-detected non-proportional hazards and sized 390 events vs 229 (the no-skill design would run at ~28% power).

Source: benchmark_analysis_2026-04-28.md in RConsortium/pharma-skills.

All 3 no-skill “wins” were skill scope-gaps (adaptive enrichment, a futility-only subgroup look) or a sandbox routing bug — not base-model superiority.

What the skill reliably added across the wins: correct gsSurv() parameterisation (unequal allocation, piecewise hazard, non-constant enrollment); enforced structured artifacts (JSON + multiplicity PNG + Word report); PFS-overpower detection with alpha-reallocation guidance; and a mandatory 5,000–10,000-rep simulation-verification step.

Section A — ADaM generation

2.7 Section A — what we’ll do

Drive the admiral skill family to derive ADaM datasets from SDTM:

Skill Produces Depends on
admiral (parent) Shared conventions — no output —
admiral-adsl ADSL (subject-level) SDTM DM, EX, DS
admiral-adae ADAE (adverse events, TEAE flag) ADSL + SDTM AE
admiral-bds ADVS / ADLB (BDS findings) ADSL + SDTM VS / LB

ADSL must be derived first — its treatment vars and population flags feed every downstream dataset.

Source data is the pharmaverse public CDISC test data (pharmaversesdtm / pharmaverseadam) — no proprietary data, safe to run live.

The agent reads skills/admiral/SKILL.md (shared conventions) first, then the child skill for the dataset in question.

2.8 Section A — how the skill behaves

When you ask for a derivation, the skilled agent will:

  • Generate code section by section, not one giant block
  • Use the native pipe |> and exprs() for admiral verb arguments
  • Use admiral date functions (never as.Date() on --DTC)
  • Emit "Y"/NA flags — never "N"
  • Drop a # REVIEW: comment at every protocol-specific decision
  • Add stopifnot() assertions (one row per USUBJID, source uniqueness, …)

Tell attendees what to look for when reviewing: the # REVIEW: markers are where they — not the agent — own the decision (population flag definitions, disposition mapping, age cut-points, TEAE window). The skill deliberately does not guess these.

Section B — Group sequential design

2.11 Section B — what we’ll do

Drive the group-sequential-design skill to design a survival trial:

  • Survival endpoints (OS / PFS / DFS), interim + final analyses
  • Alpha-spending boundaries (Lan-DeMets, Hwang-Shih-DeCani)
  • Sample-size / event targets (N-first approach)
  • Graphical multiplicity for co-primary / multi-population designs
  • lrstat simulation to verify the analytic design
  • A template-driven Word report (gsd_report.py)

Scope note the skill enforces: standard group sequential designs only. Adaptive enrichment, sample-size re-estimation, seamless dose-selection, platform trials, and non-survival primary endpoints are explicitly out of scope — the skill will say so and stop.

Tools: gsDesign, gsDesign2, lrstat, graphicalMCP, jsonlite (R) + python-docx.

[CONFIRM WITH ERIC: time budget for Section B within the 3-hour block.]

2.12 Section B — how the skill behaves

  • Asks design questions one at a time, in plain language, no defaults offered
  • Summarises all inputs in a table and waits for your confirmation
  • Computes the design, then checks interim-analysis timing against enrollment and minimum-gap constraints
  • Verifies by simulation before delivering — power within ±2 pp, type I error within ±0.5 pp
  • Writes every number to gsd_results.json; the report reads from there (no hardcoded values)

The one-artifact-per-turn pacing in the skill means the agent writes a script, stops, runs it, stops, etc. That is intentional — it keeps each step reviewable.

Section C — Modify, extend, and build a skill

2.15 Anatomy of a skill

Everything the agent needs is plain text and scripts in one folder:

skills/admiral/admiral-adsl/
├── SKILL.md                     # frontmatter + step-by-step workflow
├── references/
│   ├── admiral-functions.md     # function selection, pitfalls
│   └── adsl-conventions.md      # CDISC variable conventions
└── LICENSE
  • Frontmatter (name, description) is how the agent decides when to load the skill
  • Workflow is ordered steps with code patterns and # REVIEW: rules
  • References are read on demand, not upfront
  • A root CLAUDE.md routes the agent to the right skill

Open skills/admiral/SKILL.md and skills/group-sequential-design/SKILL.md side by side and point out the shared shape: routing / scope check, then an ordered workflow, then references and bundled scripts.
